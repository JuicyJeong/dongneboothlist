# 대표 작품(원작) 칼럼 전처리 방식 설계 및 하이브리드 파이프라인 아키텍처

> 이슈: JWMI-5 ([Stage 2] 하이브리드 전처리 파이프라인 구현 및 전체 회차 정규화·DB화)
> 작성: 2026-09-21 (KST)
> 상위 이슈: JWMI-3 (작품 관리 코드 체계 구축 및 대표 작품 칼럼 전처리·DB화 파이프라인 구현)

## 1. 배경과 요구사항

부스정보 CSV의 `대표 작품(원작)` 칼럼은 비정형 텍스트다. 오타, 띄어쓰기 오류,
약칭, 괄호 병기, 2개 이상 작품 병기(콤마 외에 공백·마침표·`/`·`&` 등), 굿즈 묶음
설명이 섞여 있다. 이를 작품 코드(`W####`)에 대응시키고, 부스-작품 매핑을 DB로
관리하며, **신규 회차 CSV 유입 시 재실행 가능한 파이프라인**이 필요하다.

제약 조건:

- 기존 `W####` 코드 재사용·재매핑 금지. 신규 작품은 `W0370`부터 부여
- 불확실한 작품 정체는 추측으로 채우지 말고 `판단 불가`로 표기
- 재현성: 같은 입력 + 같은 사전 버전 → 같은 출력 (검증 가능해야 함)
- 확장성: 사전/매핑이 갱신되어도 과거 결과를 재생성할 수 있어야 함

## 2. 전처리 방식 후보 비교

11개 회차 14,765셀, 고유 값 약 2,000종. 선택지는 다음 세 가지다.

| 관점 | A. 순수 규칙 기반 | B. 순수 LLM 배치 | C. 하이브리드 (규칙 1차 + LLM 2차) |
|---|---|---|---|
| 방식 | 사전 exact → 정규화 키 → 괄호 처리 → fuzzy(Levenshtein) | 모든 셀을 LLM에 병렬 배치 투입, 코드 반환 | 미매핑 값만 LLM에 배치 투입, 결과는 사전 별칭/신규 코드로 환원 |
| 정확도 | 알려진 별칭은 높으나 미등록 약칭·신작 처리 불가 | 문맥 이해로 신작·약칭 처리 가능하나 환각(코드 오지정) 위험 | 규칙이 확정적 매칭을 보장하고, LLM은 사람 검증을 거친 결과만 반영 |
| 비용 | 거의 0 | 셀당 토큰 비용 — 14,765셀 × 매 회차 재발생 | 미매핑 고유 값만 대상(1차 후 684종) — B 대비 약 97% 절감, 재실행 시 신규 미매핑만 증분 |
| 재현성 | 완전 결정적 | LLM 버전/온도에 따라 비결정적 — 동일 입력 다른 결과 가능 | 1차는 결정적, 2차는 검증된 매핑 파일로 고정 → 전체 재현 가능 |
| 확장성 | 사전 수동 갱신 필요 | 신규 CSV마다 전체 재실행 비용 | 신규 값만 증분 처리, 누적 학습(사전 성장) |
| 감사 가능성 | 높음 | 낮음 (판단 근거가 로그에만 존재) | 높음 (매핑 파일에 근거·표기 남음) |

### 최종 선택: C. 하이브리드

근거:

1. **재현성이 최우선 요구사항**이다. 순수 LLM(B)은 매 실행 결과가 바뀔 수 있어
   회차 간 비교·재측정이 불가능하다. 하이브리드는 LLM 판단을 "매핑 제안 → 사람
   검증 → 사전 반영"이라는 확정적 산출물로 고정하므로, 이후 정규화는 전부 결정적
   규칙으로 수행된다.
2. **비용 효율**: v1.1 사전 기준 1차 규칙만으로 82.57%가 해결된다. LLM은 남은
   684 고유 값(762셀, 전체의 5.2%)만 보면 된다. 신규 회차 유입 시에도 사전이
   성장할수록 LLM 배치는 점점 작아진다(증분 처리).
3. **정확도 안전장치**: 주의사항("추측으로 채우지 말 것")을 구조적으로 강제한다.
   LLM 결과는 코드 직접 반환 대신 `별칭 병합 / 신규 코드 / 노이즈 / 판단 불가`
   4분류 제안으로 받고, 근거를 기록한 뒤 확정분만 사전에 반영한다.
4. Stage 1(JWMI-4)에서 실제로 같은 방식(규칙 측정 → 웹 검증 기반 사전 보강)으로
   +4.99%p를 검증했다. 본 설계는 이를 파이프라인으로 자동화한 것이다.

## 3. 파이프라인 아키텍처

```
                         ┌────────────────────────────────────────┐
                         │  WORK_DICTIONARY.json (v1.2)           │
                         └──────────────┬─────────────────────────┘
                                        │
  신규/기존 *_부스정보.csv ──► ① 정규화 (규칙 1차, 결정적) ──► *_normalized.csv
                              normalize_works.py              (+ _정규화/_코드 컬럼)
                                        │
                                        ▼
                              ② 미매핑 리포트 (사람 확인용)
                              analysis/unmatched_*.csv
                              unmatched = 판단 불가 표기
                                        │
                                        ▼ (미매핑 고유 값만)
                              ③ LLM 배치 2차 (증분)
                              scripts/llm_batch_map.py
                              입력: llm_batch_input_*.csv
                              출력: llm_mapping_*.csv  ◄── LLM/사람이 작성·검증
                              (별칭/신규/노이즈/판단 불가 + 근거)
                                        │
                                        ▼ 확정분 반영
                              ④ 사전 갱신 (scripts/build_v1_2.py 계열)
                              별칭 병합 · 신규 W0370+ · noise_terms 추가
                                        │
                                        ▼ (①~④ 순환: 커버리지 수렴까지)
                              ⑤ DB 반영 (scripts/build_db.py)
                              SQLite: works 마스터 + booth_work 매핑
                                        │
                                        ▼
                              ⑥ 검증 리포트 (커버리지·멱등성·샘플)
```

단일 진입점: `pipeline.py` (⑤ 사용법은 `docs/pipeline_usage.md`)

### 3.1 ① 규칙 1차 — 정규화 엔진 (normalize_works.py 확장)

매칭 순서(셀 단위):

1. 노이즈 필터 (사전 `metadata.noise_terms`)
2. 셀 전체 exact → normalized(공백/특수문자 제거) → fuzzy(0.85)
3. 괄호 병기: 괄호 앞 텍스트, 괄호 안 약칭
4. 콤마 분리 후 각 파트 2~3 반복 (기존)
5. **[v1.2 신규] 파트별 잔여 처리 — 2차 분리자 재귀 분리**: 콤마로도 안 풀리는
   파트는 ` / & + · ` 및 공백·마침표 경계로 재분리해 각 토큰을 재매칭한다.
   - 공백/마침표 분리는 **파트 전체 매칭 실패 시에만** 폴백으로 작동하므로
     "슬램 덩크"처럼 띄어쓰기를 포함한 정식명이 잘리지 않는다
   - fuzzy는 폴백 분리 토큰에 적용하지 않는다(오탐 방지, exact/norm만)
   - 연결어(등/등등/외/및)는 사전 `metadata.split_stopwords`로 버린다
6. 그래도 남은 토큰은 사전 `metadata.llm_decisions`(LLM 2차 확정분)에 따라
   `판단 불가` 표기 또는 원문 유지

산출 컬럼: `대표 작품(원작)_정규화`, `대표 작품(원작)_코드` (코드는 `; ` 병기)

### 3.2 ②~③ LLM 배치 2차 — 증분 처리

- `scripts/llm_batch_map.py --export`: 현재 사전으로 미매핑인 고유 값 + 빈도 +
  예시 셀을 `analysis/llm_batch_input_<tag>.csv`로 내보낸다 (LLM 컨텍스트 절감을
  위해 고유 값 단위, 셀 단위 아님)
- LLM(또는 사람)이 각 값에 4분류 중 하나를 부여해
  `analysis/llm_mapping_<tag>.csv`로 작성한다:
  - `alias,<기존코드>`: 확실한 동일 작품 표기 → 사전 별칭 병합
  - `new,<신규코드>`: 사전에 없는 별개 작품 → W0370부터 순차 부여
  - `noise`: 작품 외 표기(굿즈·장르·창작·결측) → noise_terms 추가
  - `uncertain`: 정체 불확실 → **`판단 불가` 표기** (추측 금지 원칙)
  - 각 행에 `reason`(근거) 필수. 기존 코드 재매핑은 금지(코드는 불변)
- `--apply`: 확정 매핑을 사전 `metadata.llm_decisions`에 기록하고 사전을 갱신한다

### 3.3 ⑤ DB화 — SQLite 스키마

파일: `works.db` (재생성 가능 — 파이프라인 산출물)

```sql
-- 작품 마스터 (사전 기반)
CREATE TABLE works (
    code            TEXT PRIMARY KEY,   -- W0001...
    canonical_name  TEXT NOT NULL,
    origin          TEXT,               -- kr/jp/cn/en/multi/meta
    category        TEXT,               -- manga/game/webtoon...
    aliases         TEXT,               -- JSON 배열
    abbreviations   TEXT,               -- JSON 배열
    review_needed   INTEGER DEFAULT 0,
    notes           TEXT,
    dict_version    TEXT
);

-- 부스-작품 매핑 (부스 링크를 키로 작품 코드 연결)
CREATE TABLE booth_work (
    event       TEXT NOT NULL,          -- 회차 (예: 26년_7월)
    booth_link  TEXT NOT NULL,          -- 부스 고유 링크 (dongne.co ...)
    work_code   TEXT NOT NULL,          -- W####
    position    INTEGER DEFAULT 0,      -- 셀 내 순번 (복수 작품 병기)
    match_method TEXT,                  -- exact/normalized/fuzzy/...
    confidence  REAL,
    PRIMARY KEY (event, booth_link, work_code, position),
    FOREIGN KEY (work_code) REFERENCES works(code)
);

-- 매핑 근거 추적 (판단 불가·노이즈 포함, 사람 확인용)
CREATE TABLE booth_work_raw (
    event       TEXT NOT NULL,
    booth_link  TEXT NOT NULL,
    raw_value   TEXT,
    normalized  TEXT,                   -- 판단 불가 표기 포함
    codes       TEXT,                   -- 매칭된 코드 목록
    status      TEXT                    -- matched/unmatched/noise/empty
);
```

설계 포인트:

- **부스 링크를 키로 사용**: 행사마다 행 번호가 바뀌므로 링크가 유일 안정 키.
  (링크가 없는 과거 회차는 event+위치+부스명으로 대체 키 사용)
- 복수 작품 병기 셀은 `position`으로 분해 저장 (셀 = 1:N 매핑)
- `booth_work_raw`에 원문을 보존해 코드만 봐도 원래 표기를 복원할 수 있게 한다

## 4. 멱등성·재현성 보장

- 정규화: 사전 버전 + 입력 CSV가 같으면 바이트 단위 동일 결과 (무작위성 없음)
- DB 빌드: 기존 DB를 삭제 후 재생성(또는 트랜잭션 replace) → 재실행해도 동일
- 파이프라인 재실행 검증: 동일 입력 2회 실행 → SHA-256 해시 비교로 확인 (§6)

## 5. 대안 검토 시 불채택 사유 요약

- 순수 규칙(A): v1.1 기준 17.4%(미매핑+판단불가)를 사전 갱신 없이는 해소 못 함.
  신작 유입이 잦은 이벤트 도메인에서 사전 수동 갱신만으로는 확장성 부족
- 순수 LLM(B): 14,765셀 전량 배치 시 비용大, 환각으로 코드 오지정 위험, 비재현성.
  특히 "기존 코드 재매핑 금지" 제약을 LLM 자율 판단으로는 보장할 수 없음

## 6. 검증 계획

1. 샘플 정확도: 회차 1개 무작위 100셀 추출, 매핑 결과 육안 검증
2. 멱등성: `pipeline.py --all` 2회 실행 → normalized CSV 해시 일치 확인
3. 커버리지 측정: `scripts/analyze_works.py`로 v1.1 대비 v1.2 매칭률 비교
4. 미매핑 잔여: 고유 값 수·셀 수 보고 (판단 불가 포함)
